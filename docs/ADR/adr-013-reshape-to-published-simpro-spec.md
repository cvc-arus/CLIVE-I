# ADR-013: Re-shape `simpro_mock` and `simpro_client` to Simpro's published API spec

## Status

**Proposed** — 2026-10-07.

Supersedes the "Capabilities & Coverage" list of `adr-mock-simpro-api.md`
(that ADR's Decision to build a containerised FastAPI + PostgreSQL mock
stands; only its claims about route count and payload fidelity are replaced).

- **Deciders:** Al (approver), Claude (drafted)
- **Scope decisions taken by Al in conversation on 2026-10-07** are recorded
  as the recommended option in each subsection below: fidelity scope (§2), the
  clean break on the public API (§4), `columns` on both sides (§5), `Decimal`
  money (§6) and two tables for `CustomFields` (§8). They are not binding
  until Al marks this ADR Accepted.

## Context

`services/simpro_mock/` was built before anyone had read Simpro's API
reference, and `simpro_client`'s Pydantic models were then built against the
mock. Five documents — `docs/PDDs/PDD-phase3.md` (§17, §61),
`docs/scope/scope-rev2.md` §45, `docs/architecture.md` §84,
`docs/phase3/phase3-summary.md` §100 and `docs/CHANGELOG.md` §31 — state that
switching to live Simpro requires only a `SIMPRO_BASE_URL` change.

On 2026-10-07 Al supplied Simpro's official OpenAPI 2.0 specification
(`swagger.json`, 26,945,624 bytes, `info.title` "Simpro Rest API",
`version` "v1.0", 719 paths, dated 2026-08-20). Simpro's own portal
(`developer.simprogroup.com/apidoc/`) returns HTTP 403 to this environment, so
the file could not be re-fetched independently; its provenance is Al's download.

Diffing both packages against that spec, by generating payloads from its own
response schemas and feeding them to our models:

- **2 of 22** list-and-detail validation checks pass. Only `Company` passes.
- Of 70 field names declared across the 11 models that have a real endpoint,
  **22** appear in a default list response and **35** in a detail response.
  `Project` declares a further 7 against no endpoint at all.
- **4 of 12 routes do not exist** in the published API.

Representative breaks: `CompanyID` is required on eight models but is a path
parameter upstream, never a response field; `Job.Status` and `Quote.Status` are
`str` but upstream are `{ID, Name, Color}`; `Total` is `float` but upstream is
`{ExTax, Tax, IncTax}`; `Site.Address` is five flat optional columns but
upstream is a required nested object spelling the field `PostalCode`; `Asset`
overlaps reality only on `ID`; `Employee` has one `Name`, not
`GivenName`/`FamilyName`; `Attachment.ID` is a **string** upstream.

The cutover claim is therefore unverified and, on this evidence, false. The
goal of this ADR is to make it true and, more importantly, **checkable without
API access**.

## Decision

### 1. Vendor the vendor's contract, and test against it

Commit a pruned, GET-only, 25-path subset of the official spec as
`docs/contracts/simpro-openapi-v1-get-subset.json` (251 KB, versus 27 MB for
the full spec), generated by `scripts/prune-simpro-spec.py` so it is
reproducible from a future spec drop. The relevant operations contain no
`$ref`, so the subset is self-contained.

This file becomes the **normative source** for field names, types and
required/optional status, replacing
`docs/phase3/sprints/phase3-sprint4-contract.md`, which is a historical sprint
report and must not be rewritten. `src/simpro_client/CLAUDE.md` §7 is repointed
accordingly.

`tests/test_spec_conformance.py` generates two payload shapes per endpoint from
that file — `full` (every documented property) and `minimal` (required
properties only, with nullables set to `null`) — and validates the client
model. The `minimal` leg is the strict one: it proves we never require a field
Simpro may omit, and never reject a documented `null`.

Known-nonconforming combinations live in `tests/spec_conformance_baseline.json`
as data, not behind `xfail` markers, which `tests/CLAUDE.md` §7 rules out. The
test enforces the baseline in both directions: a combination outside the file
must conform, and a combination inside it that starts conforming fails until
its entry is deleted. The file can only shrink.

`tests/test_client_mock_drift.py` closes a separate gap found while planning
this work: **nothing tested that `simpro_client` could reach `simpro_mock`.**
`tests/test_simpro_mock_v2.py` drives the mock with raw `httpx` and never
imports the client; every client-side test uses `respx` and never touches the
mock. The two packages could have drifted apart with a green suite.

### 2. Fidelity scope — shape over coverage

**Recommended (Al's choice, 2026-10-07):** the full default list projection
(34 fields) plus detail fields at nesting depth ≤ 2 (~201 fields), omitting the
`Totals`, `Rates`, `Banking` and `PayRates` analytic blocks, **plus** the
`CustomFields` array on `Asset`, `Job` and `Site`. Roughly 215 fields.

Rationale: what makes a cutover safe is correct routes, names, nesting, types
and optionality — not coverage of every documented field. `SimproBaseModel`
sets `extra="ignore"`, so an omitted field is additive later and
non-breaking. `CustomFields` is in scope because that is where Simpro stores
asset serial numbers, models and manufacturers — CVC's CCTV asset data — and
omitting it would mean the mock cannot represent data CVC actually tracks.

Anything the mock serves must be correct. Anything it omits must be omitted
because the spec permits it, verified per field:

- Nullable, so `null` is legal: `Company.DefaultCostCenter`,
  `Attachment.Folder`, `Attachment.AddedBy`, `JobNote.AssignTo`,
  `JobNote.SubmittedBy`, `Site.Zone`, `Asset.CustomerContract`,
  `Asset.ParentID`, `Customer.ResponseTimes`.
- Required objects with no required inner fields, so `{}` is legal:
  `Job.ConvertedFrom`, `Asset.LastTest`.
- Required arrays, so `[]` is legal: `Job.Tags`, `Job.Technicians`,
  `Job.AdditionalContacts`, `Customer.Tags`, `Customer.PreferredTechs`.
- Required and must be populated: `Job.Customer`, `Job.Site`, `Job.Status`,
  `Job.CustomerContract`, `Asset.AssetType`, `Site.Customers`,
  `Site.PrimaryContact`, `Customer.Sites`, `Employee.DefaultZone`,
  `Employee.DefaultCompany`, `Employee.Address`, `Employee.PrimaryContact`,
  `JobNote.Visibility`, `JobNote.Reference`.

### 3. Routes

| Current | Published |
|---|---|
| `/companies/{c}/projects/` | **does not exist** — a project is a Job with `Type: "Project"` (`enum: Project\|Service\|Prepaid`) |
| `/companies/{c}/statuses/` | `/companies/{c}/setup/statusCodes/projects/` |
| `/companies/{c}/jobs/{j}/attachments/` | `/companies/{c}/jobs/{j}/attachments/files/` |
| `/companies/{c}/customers/{id}` | `/customers/individuals/{id}` and `/customers/companies/{id}`; the list carries a required `Type` discriminator and an `_href` |

The other eight collection/detail pairs already match. Read-only scope is
unaffected: every published collection route is GET-only or GET+POST, and the
client issues only GET.

### 4. Public API — a clean break

**Recommended (Al's choice, 2026-10-07):**

- Remove `Project` and `ProjectsEndpoint`. Projects are jobs filtered on
  `Type`. `SimproSettings.company_id_projects` keeps its meaning (the company
  whose jobs are `Type=Project`) and is re-documented.
- Rename `Status` → `ProjectStatusCode` and `StatusesEndpoint` →
  `ProjectStatusCodesEndpoint`.
- Split `Customer` into `CustomerSummary` (list) + `IndividualCustomer` +
  `CompanyCustomer`, served by three endpoint classes
  (`CustomersEndpoint` list-only, `IndividualCustomersEndpoint`,
  `CompanyCustomersEndpoint`). `ContactsEndpoint` stays nested under the
  polymorphic `/customers/{customer_id}/contacts/`.

This is a breaking change to the public surface that
`src/simpro_client/CLAUDE.md` §2 puts behind Al's approval. It is acceptable
now because Phase 4 has not started and nothing imports these names. Keeping
them would leave the library's vocabulary permanently disagreeing with the API
it wraps, which is the problem this ADR exists to fix.

### 5. `columns`

**Recommended (Al's choice, 2026-10-07):** both sides.

Published list endpoints return a narrow default projection — jobs and quotes
return only `ID`, `Description`, `Total`; most others return `ID` plus one
label. Wider responses require a `columns` CSV query parameter, accepted on
both list and detail routes. The client sends none today.

The client gains an optional `columns=` argument on `get`, `fetch_page` and
`iter_all` (additive, not breaking). The mock honours `columns` as a filter
over the serializer's output dict — `columns` selects **top-level keys only**,
and a selected key yields its whole nested block. `ID` is always included.

Without this, Phase 4 can only assemble full records by calling the detail
route once per item: an N+1 against a documented limit of 10 requests per
second, enforced per IP and per build.

### 6. Money

**Recommended (Al's choice, 2026-10-07):** `Decimal` in client models,
`Numeric(12, 2)` in mock columns.

Every money `number` in the spec carries `pattern (^\d+(\.\d{1,2})?$)` —
11,002 occurrences — i.e. a fixed two decimal places. Holding that as binary
floating point is wrong in a way that matters once Phase 4 renders money onto
customer-facing documents: five realistic line values sum to
`3700.2499999999995` against `Decimal`'s `3700.25`, and `ExTax + Tax` does not
reproduce `IncTax` exactly.

**Wire format, verified 2026-10-07:** Pydantic v2 serialises a `Decimal` field
to a JSON **string** (`model_dump(mode="json")` → `'1.57'`), but the spec
declares `number`. The mock must therefore emit a JSON number via a
`field_serializer` returning `float` over the `Numeric(12, 2)` column. The
client holds `Decimal` and accepts a JSON number (verified: it parses both
`1234.55` and `"1234.55"`), so the client side is safe either way.

Note the spec applies a *string* `pattern` to a `number`, which is invalid
Swagger 2.0. The payload generator tolerates it rather than crashing.

### 7. Mock response construction — a serializer layer

`routers.py` currently hand-builds every response with explicit PascalCase
keyword arguments, duplicated between list and detail: 24 construction sites
plus 12 schema classes to touch for a single field rename. Nested objects make
that unmanageable.

**Decision:** each resource gets `to_list_dict()` / `to_detail_dict()` in a new
`services/simpro_mock/simpro_mock/serializers.py`, halving the construction
sites to 12. Responses stay explicit and PascalCase; they are just factored out
of the route handlers. `services/simpro_mock/CLAUDE.md` §4 currently mandates
building them inline and is amended in the sprint that introduces serializers.

The accompanying pattern is **flat DB columns, nested wire shape, composed in
the serializer**. `Site.Address{Address,City,State,PostalCode,Country}`
composes from the five columns that already exist; `Job.Total{ExTax,Tax,IncTax}`
from three new `Numeric(12,2)` columns. This keeps schema churn proportional to
the data actually stored rather than to the shape of the JSON.

New tables are added only where a required field has no backing data: `zones`,
a `site_customers` association replacing the single `sites.customer_id` foreign
key, `asset_types`, and `customer_contracts`.

`jobs.status_id` and `quotes.status_id` are **real foreign keys** to the
reshaped status-codes table, not flat denormalised columns. The spec documents
the `Status` field in the Job POST, Job PATCH and Quote POST bodies as
`integer`, *"ID of a project status code"*, so job, quote and project statuses
share an ID space. Flat columns would let the mock emit a status ID that exists
nowhere — the class of invented convenience this ADR exists to remove.

### 8. `CustomFields` storage

The wire shape is `[{CustomField: {ID, Name, Type, ListItems}, Value}]` — a
definition plus a value.

**Options**

1. **Two tables** — a `custom_fields` definition table and a
   `custom_field_values` table keyed by resource. Mirrors how Simpro models it
   (it exposes `/setup/customFields/...` endpoints we do not implement), keeps
   definitions shared across rows, and makes the serializer a direct join.
2. **A JSON column** per resource. Fewer tables, but stores a duplicate copy
   of every definition on every row, and makes "list the custom fields
   configured on this build" unanswerable.

**Recommended (Al's choice, 2026-10-07):** option 1, two tables. The wire shape
is already normalised, and two small tables are cheaper than denormalised
duplication across three resources. This is a persistence-strategy choice,
which root `CLAUDE.md` §3 puts behind an ADR — hence its presence here.

The tables are created in Wave A's migration (S3), ahead of first use, because
`Site` lands in S4 and `Job` and `Asset` in S5.

## Alternatives Considered

**Defer until live API access exists.** Rejected. It needs no API access — only
the spec, which we now have — and the cost of deferring rises sharply: Phase 4
would build document templates against `Total: float` and `Status: str`, and
re-shaping after that is far more expensive than before it.

**Change the client only, leaving the mock as it is.** Rejected. The mock would
then be the thing the client is tested against *and* wrong, so the conformance
test would pass while every integration test failed.
`services/simpro_mock/CLAUDE.md` is explicit: when the mock differs from real
Simpro, the mock is what gets fixed.

**Full fidelity to all 763 documented leaf fields.** Rejected as poor value.
`Job` alone has 173, about 60 of them the `Totals` cost-analysis block. It
roughly triples the work to generate invented numbers nobody reads, and adds no
cutover safety over correct shapes.

**Keep the current public names and change only internals.** Rejected — see §4.

**Vendor the full 27 MB spec.** Rejected. The pruned GET-only subset is 251 KB
and self-contained, and the pruning script makes it reproducible.

## Consequences

**Good**

- The cutover claim becomes a measured number instead of an assumption:
  4 of 44 conformance checks pass today, and the target is every check passing.
- A client↔mock drift test exists for the first time, so the two packages can
  no longer diverge silently. It passes today and acts as a regression guard
  from the first sprint onward.
- The mock stops teaching the client habits real Simpro will not honour.
- Money is modelled as the fixed-point value the spec declares.

**Costs and risks**

- It is a breaking change to `simpro_client`'s public API (§4) and to the
  mock's wire contract, which `services/simpro_mock/CLAUDE.md` §3 classes as
  breaking.
- Every file under `src/simpro_client/models/` and `endpoints/`, five modules
  of the mock, three test modules and `scripts/verify-simpro-mock.py` (24
  PascalCase field lists, ~36 route literals) are rewritten across seven
  sprints. Al's decision of 2026-10-07 is to keep and update the verify script
  each sprint rather than retire it.
- Three hand-written Alembic migrations. `alembic/env.py` does not import
  `simpro_mock.models`, so `--autogenerate` would emit drops for every table.
  Because the container runs `alembic upgrade head && python -m
  simpro_mock.seed` on every start and the seed truncates with
  `RESTART IDENTITY`, there is no data to preserve: `downgrade()` may recreate
  columns empty, and each migration says so in its docstring.
- `docs/simpro-mock-api-reference.md`, `docs/architecture.md` §5.2–§5.4 and
  `docs/testing.md` all go stale and are regenerated or revised.
- The vendored subset derives from a file that cannot be re-fetched from this
  environment. If Simpro's published spec and the real API disagree, this work
  aligns us with the spec, not with the API. That residual risk is only
  closable with live access.

**Unaffected**

- Read-only scope. Synchronous throughout. Package independence. The two
  isolated PostgreSQL instances. ADR-009 (Phase 3 → 4 handoff) remains open and
  is not touched by this ADR.
