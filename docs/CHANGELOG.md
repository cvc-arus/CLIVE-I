## Phase 3 — Simpro API Integration

### Sprint 1 — Client Foundation
- Created `src/simpro_client/` package (editable install, `pyproject.toml`)
- `config.py`: `SimproSettings` via `pydantic-settings`, `SIMPRO_` env prefix, `extra="ignore"`
- `auth.py`: `AuthManager` — OAuth2 Client Credentials with token caching/refresh, API Key fallback
- `client.py`: `SimproClient` base HTTP client — GET/POST/PATCH/DELETE, 401 retry-once, structured error handling
- `exceptions.py`: typed exception hierarchy (`SimproError`, `SimproAuthError`, `SimproAPIError`, `SimproRateLimitError`, `SimproNotFoundError`)
- `logging.py`: `ContextVar`-based correlation IDs, JSON log formatter, `RequestTimer`
- 18 unit tests added (`test_auth.py`, `test_client.py`, `test_config.py`, `test_logging.py`), respx-mocked, all offline

- 2026-10-07: ADR-013 S3 (Wave A) — re-shaped `ProjectStatusCode`, `Attachment`, `JobNote`, `Company` and `Employee` to the vendored contract, client and mock together. - 2026-10-07: ADR-013 S4 (Wave B) — split `Customer` and re-shaped `Contact` and `Site`, client and mock together. The conformance baseline fell from 24 entries to 12, and the matrix grew from 44 checks to 50 as the customer split added routes, so 38 of 50 checks now pass (was 20 of 44). Customers are polymorphic upstream: `/customers/` lists both kinds with a `Type` discriminator and an `_href`, the full record lives on `/customers/individuals/{id}` or `/customers/companies/{id}`, and there is **no `/customers/{id}`**. `Customer` therefore became `CustomerSummary` + `IndividualCustomer` + `CompanyCustomer`, and `CustomersEndpoint` + `IndividualCustomersEndpoint` + `CompanyCustomersEndpoint`; the list-only `CustomersEndpoint` has `detail_path = None` and a `get()` that raises `NotImplementedError` naming the two subtype endpoints, which `tests/test_route_contract.py` now enforces for any such class. The mock's subtype detail routes are type-scoped and 404 for an id of the other kind. `Contact` dropped `CompanyID`/`CustomerID` and the single `Phone`, gaining `Title`, `Department`, `Notes`, four separate phone numbers, the eight contact-role booleans and `DateModified`. `Site` dropped `CompanyID` and its single `customer_id` FK — a site belongs to several customers, so `site_customers` replaces it, because `Site.Customers` and `Customer.Sites` are the same relation — and gained a nested `Address` (renaming `postcode` to `postal_code`), `BillingAddress` (which upstream has no `Country`), `BillingContact`, `PrimaryContact`, `PublicNotes`, `PrivateNotes`, `Zone`, `Archived`, `CustomFields` and `DateModified`. Added the two shared custom-field tables ADR-013 decided on, `custom_fields` and `custom_field_values`, consumed by Site now and by Job and Asset in Wave C; they were planned for Wave A's migration but moved here, where they are first read. `Customer.AmountOwing` is the first money field to become `Decimal` / `Numeric(12,2)`, serialised to the wire as a JSON number. One Alembic migration (`20261007_reshape_wave_b.py`, head `4c5d6e7f8091`); it round-trips, and its `downgrade()` is lossy in one documented place. `Banking` and `Rates` remain out of scope by ADR-013's fidelity decision
- 2026-10-07: ADR-013 S5 (Wave C) — re-shaped `Job`, `Quote` and `Asset`, converted money to `Decimal` / `Numeric(12,2)`, and dropped the `projects` table. **The conformance baseline is now empty: all 50 checks pass, up from 4 of 44 when the work started.** That is the point at which "switching to live Simpro is a configuration change" stops being an assumption and becomes a measured property of the code. `Job` and `Quote` list responses return only `ID`, `Description` and `Total` — the narrow projection real Simpro returns, not even including `Name` — and `Total` is a nested `{ExTax, Tax, IncTax}` object of JSON numbers, stored as three `Numeric(12,2)` columns, replacing the single `Float`. `jobs.status_id` and `quotes.status_id` are real foreign keys to the re-shaped status-codes table, because the contract documents a job's `Status` as "ID of a project status code", so flat text columns would let the mock emit a status that exists nowhere. Jobs gained `customer_id` and `site_id` foreign keys, neither of which existed, plus `type`, `stage`, `description`, `notes`, `order_no`, `request_no`, dates and `CustomFields`. `Asset` lost `AssetNo`, `Name`, `SerialNo`, `Model` and `Manufacturer` (and the unique constraint on `asset_no`): upstream an asset is identified by its `AssetType`, a new table, and the serial number, model and manufacturer live in custom fields, which is where Simpro keeps CVC's CCTV asset data. Added a `customer_contracts` table, because `Job.CustomerContract` is a required object with five required members and can be served neither as `null` nor as `{}`. **The `projects` table is gone**: its rows are now jobs with `type="Project"`, matching Simpro, which has no Projects resource; `SIMPRO_COMPANY_ID_PROJECTS` is re-documented as the company whose jobs are projects. One Alembic migration (`20261007_reshape_wave_c.py`, head `5d6e7f809102`); it round-trips, and its `downgrade()` is lossy in three documented places. Every served resource now builds its response through `serializers.py`. Fixed two defects found while building: `ConvertedFrom` was emitting `null` members where the contract has optional-but-not-nullable ones, so it is now a passthrough dict that preserves the legal `{}`; and a client field named `Date` cannot be annotated with a bare `date`, because Python binds the name before evaluating the annotation
